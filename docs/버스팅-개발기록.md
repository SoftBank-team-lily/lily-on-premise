# 클라우드 버스팅 개발 기록

온프레미스가 감당하지 못하는 요청을 클라우드(k3s)로 넘기는 기능을 만든 과정. 단계마다 문제, 원인, 해결, 측정값을 남긴다.
설계와 설정은 [README 클라우드 버스팅](../README.md#클라우드-버스팅), 실주소 테스트 방법은 [test/burst](../test/burst/README.md).

## 구성

```
사용자 → https://{app}.lilycloud.kr → Cloudflare Tunnel → 에이전트 프록시 ─┬─ 로컬 슬롯 (Docker)
                                                                         └─ 클라우드 Ingress → k3s Pod
온프레미스 앱 ─ ssh -L (lily-tunnel) ─┐
클라우드 Pod ─────────────────────────┴─ 같은 RDS (프로비저너가 만든 프로젝트 DB)
```

| 저장소 | 역할 |
|---|---|
| lily-on-premise | 프록시, 버스팅 상태 머신, DB 터널 |
| lily-builder | `/api/burst`: 클라우드 대기 배포, 레플리카 조절, DB 접속 정보 |
| lily-cicd | 배포 `host` 지정, 앱 조회, 레플리카 변경 API |
| lily-db-provisioner | 터널 주소로 접속 정보(`/env?host=&port=`), 배스천 계정 스크립트 |

## 1단계: 연결 단위 넘김 (2026-09-30)

- on-premise #1, builder #5, cicd #4
- 프록시가 로컬 동시 연결이 한도에 닿으면 새 TCP 연결을 클라우드 Ingress 로 넘긴다. Host 헤더는 그대로
- 온프레미스 배포 성공 시 같은 레포를 클라우드에 레플리카 0 으로 대기 배포 (Ingress 호스트 = 공개 주소)
- 상태 머신: `STANDBY → IDLE → SCALING → OVERFLOWING → IDLE`
- 문제: keep-alive 연결은 끝나지 않아 새 연결 수만으로는 과부하를 못 잡았다 → 처리 중 연결이 한도 이상이면 과부하로 판단
- 측정 (nip.io, 로컬 한도 4, 동시 16, 60초): 2,822건 모두 200. 3초 뒤 스케일, 약 16초 뒤 넘김, 부하 종료 20초 뒤 0

## 2단계: DB 공유 (2026-09-30)

- provisioner #1, builder #6, on-premise #2
- 온프레미스 앱과 클라우드 Pod 가 같은 RDS 프로젝트 DB 를 쓴다
- RDS 는 비공개. 에이전트가 lily-server 의 `lily-tunnel` 계정으로 `ssh -L 172.17.0.1:15432 → RDS:5432`
  - 배스천 계정은 셸 없이 RDS:5432 포워딩만 허용
  - Docker 브리지 게이트웨이에만 열려 LAN 에 노출되지 않는다
- 접속 정보는 builder → 프로비저너 `/env?host=172.17.0.1&port=15432` 로 받아 온프레미스 컨테이너에 주입
- 측정: 온프레미스에서 쓴 글을 클라우드 Pod 가 읽고, 반대 방향도 확인

## 3단계: 실주소(lilycloud.kr) 준비 (2026-09-30)

- 도메인 lilycloud.kr 네임서버를 Cloudflare 로 이전 (팀 합의: DNS 는 Cloudflare 에서 관리)
- Account API 토큰 `lily-onprem-agent`
  - 계정 전체: Cloudflare Tunnel Write
  - lilycloud.kr: DNS Write, Zone Read, SSL and Certificates Write
- 에이전트가 API 로 터널 `lily-{agentId}` 와 앱별 호스트이름을 만든다
- 계정 이메일 변경 요청이 인증되지 않은 상태로 남으면 토큰 생성이 "Please verify your email" 로 막힌다.
  같은 주소로는 재요청이 안 되어 별칭 주소로 변경 후 인증했다

## 4단계: cloudflared keep-alive 로 클라우드에 묶임 (2026-09-30, on-premise #3)

- 증상 (실주소, 동시 40, 90초): 넘김은 됐지만 부하가 끝나도 `OVERFLOWING` 에서 내려오지 않았다. 부하 후 요청 60건 모두 클라우드
- 원인: cloudflared 는 원본 연결을 keep-alive 풀로 붙잡고 재사용한다
  - 연결 단위로 넘기므로 한 번 클라우드로 간 연결은 계속 클라우드
  - 그 연결이 닫히지 않아 `remoteActive` 가 0 이 되지 않았다
- 임시 해결: 클라우드로 넘긴 연결이 응답 후 2초 조용하면 닫는다
- 측정: 1,725건 모두 200, 부하 종료 20초 뒤 IDLE, 부하 후 요청 모두 온프레미스
- 남은 문제: 클라우드로 넘어간 연결이 1개인데 요청 절반을 받았다. 분배를 정할 수 없다

## 5단계: 요청 단위 분산 (2026-10-01, on-premise #4)

- 원인 정리
  - 연결 단위로는 cloudflared 의 연결 재사용 때문에 분배를 정할 수 없다
  - 과부하를 연결 수로 판단해서 쉬고 있는 keep-alive 연결만으로 버스팅이 켜졌다.
    `/whoami` (수 ms) 부하는 실제로 앱을 포화시키지 않았는데도 스케일했다
  - 한도 확인과 증가가 따로라 동시에 들어온 연결이 한도를 넘었다 (한도 4 에서 7)
- 해결
  - 프록시를 HTTP/1.1 리버스 프록시로 바꾸고 요청마다 보낼 곳을 정한다. WebSocket(101) 이후는 바이트 그대로
  - 로컬 자리를 CAS 로 잡는다. 압력은 처리 중인 요청 수
  - 4단계의 유휴 연결 회수는 필요 없어져 제거
- 새 문제: 넘기자마자 클라우드가 503 (로컬 부하에서 424건). Deployment 는 Ready 인데 Ingress 엔드포인트 반영이 늦다
  - SCALING 에서 공개 Host 로 Ingress 에 요청해 Pod 까지 닿을 때만 OVERFLOWING
  - 클라우드가 502/503/504 를 주면 본문 없는 GET/HEAD/OPTIONS 는 로컬이 다시 처리 (`fallbackTotal`)
- 측정
  - 프록시 처리량 (로컬, keep-alive, 동시 40): 13,759 req/s. 앱 직접 22,529 req/s
  - 실주소 `/chaos/slow?ms=300`, 동시 20, 70초, 로컬 한도 4: 1,714건 모두 200, 오류 0
  - `IDLE → SCALING`(약 6초) `→ OVERFLOWING`(약 17초) `→ IDLE`(부하 종료 20초 뒤)
  - 692건(40%) 클라우드 처리, 넘김 중 로컬 처리 중 요청 4 이하, fallback 0, 부하 후 모두 온프레미스
  - `test/burst/load.sh` 로 재확인 (동시 20, 60초): 1,492건 200, 클라이언트 타임아웃(20초) 1건, 최장 14초.
    넘김 전 SCALING 약 17초 동안 로컬 처리 중 요청이 12 까지 쌓인다 → 남은 과제 '클라우드 준비 시간'

## 남은 과제

| 과제 | 내용 |
|---|---|
| 클라우드 준비 시간 | 레플리카 0 에서 넘김까지 약 17초. 워커 이미지 미리 받기, 최소 1 대기 옵션, 이른 판단 |
| 과부하 판단 | 처리 중 요청 수만 본다. 응답 지연(p95), 컨테이너 CPU 반영 |
| 에이전트 재시작 | 상태가 메모리에만 있다. 시작 시 클라우드 레플리카를 조회해 맞춘다 |
| 앱 상태 | DB 만 공유. 세션, 로컬 파일, 인메모리 캐시는 stateless 전제 또는 Redis |
| 보안 | 터널 키와 버스팅 토큰을 에이전트별로 발급 |
| 관측 | 버스팅 이벤트와 응답 비율을 모니터링으로 내보내기 |
