# 이식 전환 기획

같은 앱의 공개 주소 `https://{app}.{zone}` 를 유지한 채, 그 주소가 받는 트래픽 전체를 온프레미스와 클라우드 중 한쪽으로 옮긴다. 옮기기 전에 목적지 Ready를 확인하고, 실패하면 기존 쪽이 계속 받는다. 버스팅(넘침)과 블루·그린(버전 교체)과는 다른 동작이다.

에이전트의 `GET/POST /api/apps/{app}/home` 과 컨트롤 플레인의 같은 경로가 이 계약을 실행한다. 실주소에서 글을 주고받는 측정은 아직 없다.

## 증명하려는 것

이식은 다음이 한 번에 성립할 때 성립한다.

1. 사용자가 치는 주소가 바뀌지 않는다.
2. 전환이 끝난 뒤 새 요청은 모두 목적지로 간다. 비율로 나누지 않는다.
3. 목적지가 요청을 받을 준비가 되기 전에는 주소를 움직이지 않는다.
4. 주소 변경이 실패하거나, 변경 직후 공개 주소 확인이 실패하면 주소는 이전 쪽을 가리킨다.
5. 처리 중이던 요청과 WebSocket은 연결이 끊기기 전까지 원래 쪽에서 끝난다. 다음 연결부터 새 쪽이다.
6. 온프레미스 → 클라우드, 클라우드 → 온프레미스 둘 다 된다.
7. 전환 뒤에 같은 글이 양쪽에서 보인다. DB 가 있으면 양쪽이 같은 DB 를 쓴다. DB 가 없는 앱은 상태 없는 앱으로 보고 그대로 옮긴다.

PC가 꺼져도 주소가 살아 있는 자동 장애 조치는 이 기획의 범위가 아니다. 그건 가용성이고, 주소 변경 권한이 컨트롤 플레인에 있어야 한다. 지금은 그 권한이 에이전트의 Cloudflare API 토큰에 있다.

## 지금 구조에서 주소가 고정되는 곳

사용자 요청은 Cloudflare 가장자리 → `{app}.{zone}` CNAME → `lily-{agentId}` 터널 → `http://127.0.0.1:{proxyPort}` → 활성 슬롯이다. `CloudflareHostnameProvisioner.upsertDns` 가 CNAME 내용물을 터널(`{tunnelId}.cfargotunnel.com`, proxied, ttl 1)로 둔다. `putIngress` 는 그 호스트의 오리진을 로컬 프록시로 둔다. 두 호출이 `ensureHostname` 한 메서드 안에 있다.

클라우드 Ingress도 같은 Host를 받는다. 버스팅은 에이전트 프록시가 `BURST_INGRESS_HOST` 로 요청을 넘길 뿐, DNS는 터널에 남는다. `UpstreamProxy` 가 모든 요청을 클라우드로 보내도 입구는 PC다. PC가 꺼지면 클라우드 Pod가 Ready여도 공개 주소는 죽는다.

그래서 이식 전환은 프록시 upstream을 바꾸는 일이 아니다. **같은 CNAME 레코드의 내용물**을 바꾼다.

| 거점 | CNAME 내용물 | 그 다음 경로 |
|---|---|---|
| `onprem` | `{tunnelId}.cfargotunnel.com` | 터널 ingress → 로컬 프록시 → 슬롯 |
| `cloud` | 설정으로 받은 클라우드 오리진 호스트 | Cloudflare → 클러스터 Ingress → Pod |

레코드 타입은 계속 CNAME이다. A 레코드로 바꾸면 지웠다가 다시 만드는 동안 이름이 비고, 실패해도 이전 레코드가 없다. 클라우드 쪽은 IP가 아니라 호스트 이름이어야 한다. 값 이름은 `CUTOVER_CLOUD_ORIGIN` 이다. 예: Ingress 앞에 이미 있는 호스트. 비어 있으면 전환 API는 거절한다.

ttl 1, proxied 유지는 지금 `upsertDns` 와 같다. 인증서 팩은 호스트 기준이라 거점을 바꿔도 다시 주문하지 않는다.

## 상태

에이전트 하나의 공개 주소는 하나이고, 앱도 하나다. 거점도 하나다.

```
ONPREM ──요청──▶ MOVING_TO_CLOUD ──공개 확인──▶ CLOUD
CLOUD  ──요청──▶ MOVING_TO_ONPREM ──공개 확인──▶ ONPREM
```

어느 MOVING 에서든 준비 실패나 확인 실패면 출발 거점으로 돌아간다. 진행 중에는 두 번째 전환을 받지 않는다.

상태는 프로세스 메모리에 둔다. 버스팅 상태와 같은 제약이다. 재시작 시 DNS를 읽어 거점을 복구한다. CNAME이 터널이면 `ONPREM`, 클라우드 오리진이면 `CLOUD`, 그 외면 전환을 거절하고 이벤트로 남긴다.

## 온프레미스에서 클라우드로

전제: 지금 거점이 `ONPREM` 이고, 아래 거절 조건을 통과했다.

1. 클라우드에 같은 잡의 배포가 있게 한다. 버스팅 대기 배포(`POST /api/burst/apps/{app}/standby`)가 이미 그 잡으로 끝나 있으면 빌드를 다시 하지 않는다. 없거나 잡 id가 다르면 standby를 요청하고 SUCCEEDED까지 기다린다. 타임아웃은 대기 배포와 같은 15분이다.
2. 레플리카를 서비스 수(기본은 `BURST_REPLICAS`)로 올린다. `IngressProbe` 와 같이, Deployment Ready만 보지 않고 공개 Host로 Pod까지 닿는지 확인한다. 제한은 180초다. 닿지 않으면 레플리카를 원래 대기 수로 되돌리고 거점은 `ONPREM` 이다.
3. CNAME 내용물만 클라우드 오리진으로 PUT 한다. 터널 ingress 규칙은 지우지 않는다. 롤백할 때 다시 쓰려면 규칙이 남아 있어야 한다.
4. PUT이 실패하면 DNS는 그대로 터널이다. 클라우드 레플리카는 대기 수로 되돌린다.
5. PUT이 성공하면 에이전트 바깥에서 `https://{app}.{zone}` 를 연다. 경로는 canary 경로, 없으면 헬스 경로이고 `tcp` 면 `/` 이다. 5xx와 연결 실패는 실패다. 실패하면 CNAME을 터널로 되돌리고, 그것도 실패하면 거점을 `MOVING_TO_CLOUD` 에 남기고 이벤트로 알린다. 성공한 되돌리기 전에는 로컬 슬롯을 멈추지 않는다.
6. 공개 확인이 성공하면 거점은 `CLOUD` 다. 프록시 넘김(`overflowTo`)은 끈다. 로컬 슬롯은 30초 동안 둔 뒤 멈춘다. 처리 중인 터널 연결과 WebSocket이 그 안에서 끝나게 하려는 것이다. 멈춤에 실패해도 거점은 클라우드다. 사용자 요청은 이미 클라우드를 본다.

이 30초 동안 버스팅 틱은 레플리카를 내리지 않는다. 거점이 클라우드가 된 뒤에는 버스팅 상태 머신을 `OFF` 로 두고, `scale(0)` 을 호출하지 않는다. 버스팅이 한가하다고 판단해 레플리카를 0으로 내리면 공개 주소의 목적지가 사라진다.

## 클라우드에서 온프레미스로

전제: 지금 거점이 `CLOUD` 이고, 에이전트가 연결되어 있다. 로컬 슬롯을 띄울 주체가 에이전트뿐이기 때문이다.

1. 클라우드에 올라가 있는 것과 같은 잡으로 `OnPremPipeline` 을 실행한다. 체크아웃, 빌드, 스키마, 후보 슬롯, 루프백 헬스, canary 판정까지는 지금 파이프라인과 같다.
2. 파이프라인이 끝에서 하는 프록시 `route` 는 한다. 이 시점의 사용자 트래픽은 아직 클라우드이므로, 프록시 변경은 터널 쪽을 미리 맞춰 두는 일이다. 공개 CNAME은 아직 클라우드 오리진이다.
3. 터널 ingress가 `http://127.0.0.1:{proxyPort}` 인지 `putIngress` 로 맞춘다. DNS는 이 호출에서 건드리지 않는다. `ensureHostname` 을 그대로 쓰면 DNS까지 터널로 바뀌므로, 오리진 맞추기와 CNAME 변경을 나눈다.
4. 루프백 헬스가 이미 통과한 뒤에만 CNAME을 터널로 PUT 한다. 후보 기동이나 헬스가 실패하면 CNAME은 클라우드 오리진이고, 후보는 지금 파이프라인처럼 지운다.
5. PUT 성공 뒤 공개 주소 확인은 온프레미스 방향과 같다. 실패하면 CNAME을 클라우드 오리진으로 되돌린다. 되돌리기가 성공하면 방금 띄운 로컬 슬롯을 지우고 거점은 `CLOUD` 다.
6. 공개 확인이 성공하면 거점은 `ONPREM` 이다. 30초 뒤에 클라우드 레플리카를 대기 수(`BURST_WARM_REPLICAS`, 0이면 0)로 내린다. 그 전에 내리지 않는다. 스키마는 되돌리지 않는다. 같은 DB에 이미 적용돼 있다.

## 거절

전환을 시작하기 전에 거절하면 DNS는 호출하지 않는다.

| 조건 | 이유 |
|---|---|
| `CUTOVER_CLOUD_ORIGIN` 이 비었거나 IP다 | CNAME 타입을 유지할 수 없다 |
| Cloudflare API 네 값이 없다 | 주소가 플랫폼 존이 아니다. quick tunnel은 기동마다 바뀐다 |
| 저장소에 Dockerfile이 없고 잡에도 본문이 없다 | 클라우드 빌드는 레포의 Dockerfile을 쓴다. 에이전트가 만든 Dockerfile은 클라우드로 가지 않는다 |
| compose만 있다 | 온프레 파이프라인이 이미 배포를 중단한다 |
| 양쪽 잡 id가 달리다 | 다른 버전으로 주소를 넘기지 않는다. 같은 잡으로 맞춘 뒤에만 진행한다 |
| 이미 MOVING 이다 | 주소 변경은 한 번에 하나다 |
| 클라우드 → 온프레미스인데 에이전트에 잡을 실행할 Docker가 없다 | 목적지를 만들 수 없다 |

세션을 DB 밖에 두는 앱은 이 계약 밖이다. 전환은 막지 못하고, 설계 문서의 남은 제약 그대로다. 공유되는 것은 DB뿐이다.

## 버스팅, 블루·그린, 롤백

- 블루·그린은 한 거점 안의 버전 교체다. 온프레 거점이면 프록시 upstream, 클라우드 거점이면 lily-cicd의 Service selector다. 거점 전환 API는 그 전환을 대신하지 않는다.
- 버스팅은 거점이 `ONPREM` 일 때만 동작한다. 넘침은 요청 일부이고, 거점 전환은 주소 전체다. 거점이 `CLOUD` 인 동안 `CloudBurst.tick` 은 scale을 호출하지 않는다.
- `POST /api/apps/{app}/rollback` 은 지금처럼 직전 온프레 슬롯으로 프록시를 되돌린다. 거점이 클라우드일 때 이 호출은 거절한다. 프록시는 사용자 경로에 없다. 거점을 되돌리려면 반대 방향 전환을 호출한다.
- 프론트의 배포 위치(`cloud` / `onprem`)는 처음 올릴 곳을 고르는 값이다. 전환 API가 성공한 뒤에 그 값을 맞추는 일은 후속이다. 1차 구현은 에이전트 API와 컨트롤 플레인 메시지로 끝낸다.

## API

에이전트가 받는다. 컨트롤 플레인 주소가 있으면 롤백과 같이 WebSocket 메시지로도 받는다.

```
GET  /api/apps/{app}/home
POST /api/apps/{app}/home    { "home": "cloud" | "onprem" }
```

GET은 거점, 단계, 공개 호스트, CNAME이 가리키는 내용물, 최근 이벤트다. POST는 202와 진행 레코드를 돌려주고, 이미 그 거점이면 200으로 현재 상태를 돌려준다. 거절은 400과 `message` 다.

환경 변수는 버스팅에 필요한 것(builder URL, 토큰, Ingress, 공개 호스트, DB)에 오리진 호스트만 더한다.

| 변수 | 기본 | 설명 |
|---|---|---|
| `CUTOVER_CLOUD_ORIGIN` | 비움 | 클라우드 거점의 CNAME 내용물. 호스트 이름 |

## 구현 순서

1. `ensureHostname` 을 둘로 나눈다. 터널 ingress·인증서와, CNAME 내용물 지정. 지금 배포 경로는 내용물을 터널로 지정해 동작이 같아야 한다.
2. DNS를 읽어 거점을 정하는 조회와, 내용물만 바꾸는 호출. 실패하면 예외이고 레코드는 이전 값이다. Cloudflare 없이 이 순서만 보는 테스트를 둔다.
3. 전환 상태 머신. 준비 확인은 기존 `IngressProbe`, 로컬 헬스는 기존 `HealthProbe`, 공개 확인 실패 시 CNAME 되돌리기.
4. `CloudBurst` 가 거점 `CLOUD` 와 MOVING 중에는 scale 하지 않게 한다. 온프레 → 클라우드 준비에 standby·scale·Pod 확인을 재사용한다.
5. `POST/GET /api/apps/{app}/home` 과 컨트롤 플레인 메시지. 거절 조건은 상태 머신 앞에서 검사한다.
6. 측정 기록을 `docs/버스팅-개발기록.md` 와 같은 형식으로 남긴다. 자동 테스트는 Docker와 Cloudflare에 붙지 않는다.

## 검증

자동 테스트는 가짜 Cloudflare와 가짜 builder로 다음만 본다.

- 준비 확인 전에 CNAME PUT이 없다.
- PUT 실패 후 거점과 레플리카 대기가 원래다.
- 공개 확인 실패 후 되돌리기 PUT이 이전 내용물이다.
- 거점 `CLOUD` 에서 버스팅 틱이 `scale` 을 호출하지 않는다.
- database 없음, Dockerfile 없음, 잡 id 불일치는 PUT 없이 400이다.

손으로 보는 시나리오는 버스팅 검증과 같은 앱·같은 DB다.

- 온프레미스에서 쓴 글이 전환 직후 클라우드에서 보인다. 주소 막대는 `https://{app}.{zone}` 이다.
- 클라우드에서 쓴 글이 반대 전환 직후 온프레미스에서 보인다.
- 공개 확인을 일부러 실패시키면 주소가 이전 거점으로 돌아가고, 그 주소에서 이전 글이 보인다.
- 전환 후 에이전트 프로세스를 멈춰도 클라우드 거점의 주소는 응답한다. 다시 온프레미스로 오는 전환은 에이전트를 띄운 뒤에만 된다.

## 범위 밖

- 에이전트 사망을 컨트롤 플레인이 감지해 DNS를 넘기는 자동 조치
- Cloudflare Load Balancing으로 비율을 나누는 점진 전환. 클라우드 배포의 canary weight는 거점 안의 버전 교체에 그대로 둔다
- 세션, 로컬 파일, 인메모리 캐시를 맞추는 저장소
- 프론트 배포 위치 라디오를 전환 버튼으로 바꾸는 일
