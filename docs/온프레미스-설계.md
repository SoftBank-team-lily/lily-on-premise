# 온프레미스 설계

사용자 PC에서 Git 저장소를 받아 로컬 Docker로 띄우고, 준비된 뒤에만 공개 주소를 그 버전으로 넘기는 에이전트입니다. 클러스터와 이미지 레지스트리는 쓰지 않습니다. 아래는 그 구조를 고른 과정이고, 동작은 현재 코드 기준입니다.

## 증상

클라우드 배포는 새 버전이 Ready가 된 뒤에 Service selector를 바꿉니다. 같은 약속을 사용자 PC에서 지키려면 다음이 그대로 드러났습니다.

1. 새 컨테이너가 뜨는 즉시 공개 주소가 그 컨테이너를 보면, 헬스 체크 전에 사용자 요청이 실패합니다.
2. 배포마다 터널을 컨테이너 포트에 다시 열면, 공개 주소가 바뀌거나 준비되지 않은 포트를 가리킵니다.
3. HTTPS 인증서를 에이전트 머신에서 발급하면 비밀키가 사용자 PC에 남습니다.
4. 배포 잡을 인바운드로 받으려면 사용자 네트워크의 포트를 열어야 합니다.
5. Dockerfile을 사용자 PC의 모델이 만들면 API 키가 그 PC에 있어야 합니다. compose만 있는 저장소는 컨테이너가 여러 개라, 슬롯 하나의 upstream으로 트래픽을 옮길 수 없습니다.
6. 로컬이 감당하지 못하는 요청을 클라우드로 넘길 때, cloudflared는 keep-alive 연결 몇 개에 요청을 몰아 보냅니다. 연결 단위로 나누면 한 번 클라우드로 간 연결이 부하가 끝나도 클라우드에 남고, 요청이 어느 쪽으로 갈지 정할 수 없습니다. 레플리카 0에서 Pod를 띄우면 Ingress가 Pod까지 닿기 전에 넘긴 요청이 503이 됩니다.

## 원인

1. 이 모듈은 Kubernetes Service가 없습니다. 컨테이너 포트가 곧 입구이면, 기동과 트래픽 전환이 한 동작이 됩니다.
2. Cloudflare Tunnel의 origin이 슬롯 포트이면, 슬롯을 바꿀 때마다 ingress를 다시 써야 합니다. `LocalExposure`는 프로세스가 켜질 때 프록시와 터널을 한 번만 엽니다.
3. 사용자에게 주는 주소는 `https://{appName}.{zone}`입니다. TLS를 에이전트에서 끝내면 인증서 개인키가 그 머신에 있습니다. `CloudflareHostnameProvisioner`는 인증서를 Cloudflare 엣지에 둡니다.
4. 에이전트는 사용자 네트워크 안에서 동작합니다. `WebSocketControlSession` 주석대로, 잡을 받으려고 인바운드 포트를 열지 않습니다.
5. 슬롯 전환의 단위는 컨테이너 하나입니다. `StackAnalyzer`는 compose만 있으면 배포를 중단합니다. 컨트롤 플레인이 Dockerfile 본문을 잡에 실을 수 있고, 에이전트는 그 본문이 없을 때만 로컬에서 고릅니다.
6. `UpstreamProxy` 주석대로, 앞단의 keep-alive 때문에 연결 수로는 분배를 정할 수 없습니다. `CloudBurst` 주석대로, 레플리카 0에서 Spring 앱을 띄우면 Ingress가 Pod까지 닿는 데 20~40초가 걸립니다. 그 사이에 넘기면 로컬에 요청이 쌓이거나 게이트웨이 오류가 납니다.

## 분석

클라우드 경로의 전환은 “입구는 유지하고, 입구가 가리키는 대상만 바꾼다”입니다. 온프레미스에서 그 입구에 해당하는 것은 Service가 아니라 루프백 프록시입니다.

- 터널 origin을 프록시 포트로 고정하면, 배포마다 바뀌는 값은 upstream 포트뿐입니다.
- upstream을 바꾸기 전에 후보 포트만 헬스 체크하면, 실패해도 기존 슬롯의 트래픽은 유지됩니다.
- 호스트이름과 인증서 등록은 Ready 이후, upstream 변경 이전에 둡니다. API가 실패하면 공개 주소는 아직 이전 슬롯입니다.
- 버스팅도 같은 프록시 안에서 요청마다 로컬 포트와 클라우드 Ingress 중 하나를 고릅니다. 공개 호스트는 유지하고, Host 헤더도 그대로 넘깁니다.
- 대기 Pod가 이미 Ingress에 닿아 있으면 스케일 업을 기다리지 않고 넘길 수 있습니다. 없으면 Deployment Ready만으로는 부족하고, 공개 Host로 Pod까지 닿는지 확인한 뒤에 넘깁니다.

에이전트 하나의 공개 주소는 하나입니다. `SlotBook`은 그래서 트래픽을 받는 앱도 하나로 둡니다.

## 해결

배포는 `OnPremPipeline`이 다음 순서로 처리합니다.

1. `git clone` 후 Dockerfile을 정합니다. 우선순위는 잡에 실린 본문, 저장소의 `Dockerfile`, Gradle · Maven · Node · Python 생성입니다. compose만 있으면 중단합니다.
2. 이미지를 `lily-onprem/{appName}:{jobId}`로 로컬 빌드합니다. 레지스트리에 올리지 않습니다.
3. 마이그레이션 파일이 있으면 같은 DB에 스키마를 적용합니다. 실패하면 컨테이너를 만들지 않고 upstream은 그대로 둡니다. 적용한 뒤에는 `SPRING_FLYWAY_ENABLED=false`를 넣어 앱이 같은 스크립트를 다시 실행하지 않게 합니다. 그 다음 단계가 실패하면 적용된 스키마는 남겨 둡니다.
4. 프록시 upstream이 blue 포트이면 후보는 green, 그 외(첫 배포의 0 포함)는 blue입니다. 트래픽을 받는 컨테이너를 제외한 나머지 컨테이너를 지운 뒤, 후보만 `127.0.0.1:{슬롯포트}:{컨테이너포트}`로 띄웁니다. 메모리·CPU·프로세스 한도와 `no-new-privileges`를 붙이고 capability는 뺍니다. 1024 미만 포트만 `NET_BIND_SERVICE`를 넣습니다.
5. 헬스 체크는 프록시를 거치지 않고 후보 포트에 보냅니다. HTTP면 GET, 경로가 `tcp`면 포트 연결입니다. 기본 제한은 180초입니다. 클라우드 기동 프로브(5초 간격, 36회)와 같은 예산입니다. 실패하면 후보만 삭제하고 upstream은 그대로 둡니다.
6. 이전 슬롯이 있으면 전환 전에 후보 루프백만 판정합니다. 경로는 canary 경로, 없으면 헬스 경로이고 `tcp`면 `/`입니다. 5xx와 연결 실패를 에러로 셉니다. 거절하면 후보만 삭제하고 upstream은 그대로 둡니다. 첫 배포는 판정하지 않습니다.
7. API 자격 증명이 있으면 `https://{app}.{zone}`의 터널 ingress, proxied CNAME, 필요 시 Advanced Certificate를 맞춥니다. origin은 `http://127.0.0.1:{proxyPort}`입니다. 실패하면 후보를 지우고 upstream은 바꾸지 않습니다.
8. 프록시 upstream만 후보 포트로 바꿉니다. 이 호출이 실패하면 후보를 삭제합니다. 성공하면 이전 이미지 태그를 기억한 뒤 이전 슬롯을 정지합니다. 정지에 실패해도 새 슬롯은 지우지 않습니다. 롤백은 그 이미지로 이전 슬롯을 다시 띄운 뒤 upstream을 되돌립니다. 입구는 컨트롤 플레인 메시지와 `POST /api/apps/{app}/rollback`입니다. 스키마는 되돌리지 않습니다.

프록시는 루프백만 듣고, upstream이 0이면 503을 반환합니다. 전환은 다음 요청부터 적용되고, 처리 중인 요청은 기존 포트에서 끝납니다. WebSocket(101) 이후는 바이트를 그대로 잇습니다.

잡은 기동 시 컨트롤 플레인으로 연 WebSocket 하나로 받습니다. 주소가 비어 있으면 소켓을 열지 않고, `POST /api/jobs`로 같은 파이프라인을 실행합니다. 끊기면 5초 간격으로 다시 접속합니다.

버스팅(`BURST_ENABLED`)은 온프레미스 배포가 성공하면 같은 레포를 클라우드에 대기 배포합니다. 상태는 `STANDBY → WARMING → IDLE → SCALING 또는 OVERFLOWING → IDLE`입니다.

- 기본 `warmReplicas`는 1입니다. Ingress로 Pod까지 닿으면 넘김을 켭니다. 180초 안에 안 닿으면 레플리카를 0으로 되돌리고, 넘길 때 띄우는 방식으로 동작합니다.
- 로컬이 동시에 처리하는 요청은 기본 8입니다. 자리는 `compareAndSet`으로 잡습니다. 한도에 닿은 상태가 `scaleUpAfterSeconds`(기본 3초) 동안 이어지면, 대기 Pod가 있으면 바로 `OVERFLOWING`으로 레플리카를 올리고, 없으면 `SCALING`에서 Pod까지 닿은 뒤에만 넘깁니다.
- 클라우드가 502, 503, 504를 주면 본문 없는 GET, HEAD, OPTIONS는 로컬이 다시 처리합니다. 연결 자체가 실패하면 그 요청은 로컬로 보냅니다.
- `cooldownSeconds`(기본 30초) 동안 한가하면 레플리카를 대기 수로 줄입니다. 대기 Pod가 없으면 넘김을 끄고 0으로 둡니다.
- 잡에 `database`가 있으면 SSH 로컬 포워딩으로 클라우드와 같은 DB에 붙입니다. 터널은 Docker 브리지 게이트웨이에만 엽니다. 접속 정보는 lily-builder를 거쳐 받고, 로그에는 키 이름만 남깁니다.

## 결과 및 성과

- 공개 주소는 재배포해도 `https://{appName}.{zone}`으로 유지됩니다. 바뀌는 것은 프록시 upstream입니다. API 자격 증명이 없으면 주소는 루프백 HTTP이거나 기동마다 바뀌는 quick tunnel입니다.
- Ready 이전의 체크아웃, 빌드, 헬스, 호스트이름, upstream 변경 실패는 기존 슬롯의 트래픽을 바꾸지 않습니다. 첫 배포에서 upstream이 0인 동안 공개 주소의 요청은 503입니다.
- upstream을 옮긴 뒤 이전 슬롯 정지에 실패해도 새 슬롯은 남습니다. 사용자 요청은 이미 새 포트를 봅니다.
- 컨테이너는 루프백에만 포트를 엽니다. 빌드와 실행은 `lily.agent.sandbox` 한도(기본 2g, CPU 1, 프로세스 1024) 안입니다. 에이전트가 만든 Dockerfile은 의존성 `RUN`만 네트워크를 쓰고, 호스트 디렉터리와 Docker 소켓은 넘기지 않습니다. 이미지 태그에는 레지스트리 호스트가 없습니다. `APP_COLOR`는 슬롯 이름, `APP_VERSION`은 잡 id이며, 요청 `env`로 이 두 값을 바꾸지 못합니다.
- 버스팅을 요청 단위로 바꾼 뒤의 측정은 `docs/버스팅-개발기록.md`에 있습니다. 실주소에서 `/chaos/slow?ms=300`, 동시 20, 70초, 로컬 한도 4일 때 1,714건이 모두 200이었고, 그 중 692건(40%)을 클라우드가 처리했습니다. 넘기는 동안 로컬에서 처리 중인 요청은 4 이하였습니다. 부하가 끝난 뒤 20초 후에는 다시 온프레미스로 돌아왔습니다.
- 같은 DB를 쓰는 검증에서는 온프레미스에서 쓴 글을 클라우드 Pod가 읽고, 클라우드 Pod에 쓴 글을 스케일 다운 뒤 온프레미스에서 읽었습니다.
- 에이전트가 다시 떠도 공개 주소가 끊기지 않습니다. 기동할 때 떠 있던 앱 슬롯을 프록시에 다시 붙이고, 그 앱이 쓰던 RDS 터널을 열고, 켜 둔 버스팅을 클라우드에 남은 대기 배포로 이어 갑니다. 앱 컨테이너는 `--restart unless-stopped`라 PC를 다시 켜도 뜹니다. `docker restart` 중 요청 39건이 모두 200이었습니다.
- RDS 터널은 끊기면 5초 안에 다시 엽니다.
- PC가 꺼졌을 때는 lily-builder의 엣지 Worker가 요청을 클라우드 대기 Pod로 다시 보냅니다. 에이전트를 30초 멈춘 동안 요청 실패가 0건이었습니다 (lily-builder `docs/장애-자동-전환.md`).

남은 제약은 코드와 개발 기록이 같이 가리킵니다. 롤백 기록과 잡 목록은 프로세스 메모리에만 있습니다. 과부하 판단은 처리 중인 요청 수만 봅니다. 세션, 로컬 파일, 인메모리 캐시는 공유하지 않습니다.
